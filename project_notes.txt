Yes, your instinct is right — and it's worse than just "3 pages instead of 5 chunks." Look at what's actually in a leaf chunk's payload right now: chunk.py's _make_leaf stores the full entity dict (exercise name, sets, reps, RIR, rest, video_url) directly on every weight_exercise leaf. That's already the complete, self-contained answer — nothing more is needed from the parent.

So a blanket "always resolve child → parent" retriever is pure waste here: for 7 chest exercises spread across 1–3 pages, you'd pull in entire page tables (every OTHER exercise on those pages too, headings, markdown table syntax) just to re-derive data you already had in the leaf's entity field. That's strictly more tokens for zero new information — the parent-child pattern earns its keep when the child alone lacks context (a terse snippet that needs its surrounding paragraph), not when the child is already a fully structured record.

Recommendation: don't apply parent-fetching uniformly. Use chunk_type to decide — weight_exercise/cardio/glossary/advice/program_structure leaves are self-contained (their entity field has everything), so answer straight from the leaf hits, no parent lookup. Only fall back to the parent's cleaned_text for chunk_type="section" (the fallback leaf for "other"-category pages), since that's the one case where the leaf's embed_text is a lossy trim of prose that actually needs the fuller parent text.

Real gap, and it's the same one as the day field issue from earlier, just now concrete: today it would require two independent semantic hops, chained with nothing solid linking them.

Hop 1 works fine: the program_structure page produces one leaf per day with embed_text = "TRAINING SPLIT > Day 1: chest & back" and entity = {"day_number": 1, "target": "chest & back"} (chunk.py's _program_structure_leaves) — a query mentioning "day 1" would retrieve that fine and resolve target = "chest & back".

Hop 2 is the problem: nothing connects that resolved target string to the actual weight_exercise page for that day. Each exercise-table page only has a page_topic (e.g. "Chest & Back") inferred by a separate LLM call, on a separate page, with no cross-reference to the day number at all. So step 2 becomes a second fuzzy vector search using the resolved target as a query, hoping page_topic phrasing lines up closely enough — "chest & back" vs "Chest & Back" will probably match, but there's no guarantee across a whole document (different casing, "Chest/Back," synonyms, etc.), and a single miss here just silently returns the wrong day's exercises with no error.

The fix is at extraction time, not query time: give each weight_exercise/cardio page a day_number field directly (resolved from the split table during extraction, or just asked of the model per page), so day-scoped queries become an exact filter instead of a second semantic guess.
