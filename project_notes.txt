Why headers matter (page 2)
Heading isn't just a label — it gets baked directly into embed_text (the string that actually gets embedded and searched) for most categories: weight_exercise/cardio ("{heading} > {name}: ..."), advice ("{heading} - {topic}: ..."), program_structure ("{heading} > Day {n}: ..."), and the generic fallback. That's why it matters in general — it's how a query like "chest and back exercises" gets a lexical/semantic boost from "chest & back" literally sitting in the embedded text.

But glossary is the one category that deliberately skips it — embed_text = f"{term}: {explanation}", no heading prefix (from our earlier design: a glossary term is self-contained, heading noise would just dilute it). Page 2's actual category is glossary, so the "Reps in Reserve" mislabel only touches the parent record's stored heading field (cosmetic/provenance metadata) — it never reaches anything that gets searched. Concretely: not worth fixing.

Page 10 — different story
Its category is weight_exercise, which does embed the heading. So "Page 11" instead of "LEGS" is a real retrieval loss — every exercise on that page loses the one word ("LEGS") a query would naturally match on. This is the one heading gap that actually matters.

Minimal fix, staying inside "never merge pages": when a page has no heading of its own, carry forward the previous page's heading as a label only — content stays exactly as its own page/section, nothing gets concatenated. That's a metadata inheritance, not the section-merging we removed. Want me to add that?

The native-text-recovery mechanism
Right idea, but a raw "is the PyMuPDF text already in the markdown" check will misfire constantly — OCR reformats everything (line breaks, preprocess.py's term normalization turns "RIR" into "Reps in Reserve", tables become TABLE[type=data] blocks). A native paragraph will almost never appear as an exact substring of the OCR'd markdown even when the content is actually covered, so you'd get false "missing" hits on nearly every page and start appending redundant noise everywhere.

Better trigger: reuse the same idea normalize_extract.py already uses for needs_review — compare number tokens, not raw text. Extract the distinct numbers from PyMuPDF's native text vs. the OCR markdown for that page; if native has numbers the OCR output doesn't (exactly what happened on page 16 — 35, 4, 7 never showed up in the OCR'd "CARDIO/DAILY STEPS" text), that's a sharp, cheap, false-positive-resistant signal that real data got dropped, not just reformatted. When it fires, append the native text as a distinct supplementary block (not merged/replaced) so classification still gets a shot at it.
